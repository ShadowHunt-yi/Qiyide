# 知识库与业务审查联动改造

日期：2026-11-11。承接业务审查工作台方案，用户已要求将知识库一并改造。

## 这批的边界

先交付可信知识与审查联动的基础版本，而不是一次实现完整的多项目任务系统。

- [x] 知识概览默认入口：按业务用途与待处理状态组织，不以图谱规模代表完成度。
- [x] 确认记录绑定正文、规则范围及来源内容；旧知识保持可读，不自动背书。
- [x] AI 更新已确认内容时保存候选版本；确认候选前检查基线冲突。
- [x] 同一套知识上下文供人预览/导出及 AI 审查使用；排除草稿、过期和无法核验内容。
- [x] 结构审查区分待决定、待修改和已处理，明确不代表业务验收。
- [x] 新增回归测试，跑知识库独立测试与可用的整包编译验证。

## 已确认的问题

1. 条目解析对缺失/未知 status 默认 confirmed，没有可追溯人工确认依据。
2. applyDraft(update) 直接替换或追加到已有条目，再改成 draft；已确认正文没有保护。
3. WikiCoherence 的过期关联主要检查路径是否存在，不检查来源内容版本。
4. WikiCurator 将草稿和其他条目摘要一起提供给模型，没有明确可信边界。
5. 默认界面强调识别、锁定、建档、草稿清空，不能回答哪些知识可作为当前依据。
6. 结构结论把所有已决定 ID 一并视为处理完成，违规项也可能通向“分支审完”。

## 实施约束

- 不改动用户现有的编辑器折叠验证修改和 memory 文件。
- 不批量重写实际业务仓库知识，不调用真实模型，不提交或推送代码。
- 沿用 Markdown；确认元数据及候选版本向后兼容。旧文件只在用户保存/确认时改写。
- 来源校验只读取当前仓库内有界的普通文件；目录/业务包别名/越界路径明确标为未核验。
- 人工约定不等于代码已实现。未绑定代码的业务规则可作为约定，不能当成实现证明。
- 这批的上下文是知识快照；完整任务契约、验收执行器和跨项目待处理仍属后续里程碑。
