## 1. 功能架构：围绕“人做判断”，而不是“人读更多内容”

### 1.1 产品定位

> **一个让 AI 承担实现与证据整理、让人掌握业务方向的 IDE。**
> 人不必追读每一行代码，但必须知道：AI 在实现什么、关键行为如何变化、哪些结论有证据、还有什么必须由自己决定。

| 用户的核心目标 | 产品应承担的责任 | 用户能感知的结果 |
| --- | --- | --- |
| AI 更深入参与 IDE | 把任务、实现、测试、解释和反馈连接起来，而不只是增加聊天窗口 | 一条修改意见能回到对应任务，并带着验收条件交给 AI |
| 人转为业务与主逻辑审查者 | 把代码差异转为“目标—行为—规则—影响—证据” | 先看懂业务变化，需要时再查看关键代码 |
| 多项目并行，降低心智负担 | 保存每个任务的已知事实、决定和未决问题；切换时只报告新增信息 | 不必重读聊天记录，也不会把另一个项目的判断带过来 |

**“心里有底”不是界面给出一个绿色分数。** 它意味着：用户知道结论根据什么得出、适用到哪个版本、哪些问题仍然未知。

### 1.2 为什么当前描述还不够

| 当前页面/实现 | 能回答什么 | 不能据此回答什么 |
| --- | --- | --- |
| 新增跨域引用、文件数、引用次数 | 结构关系变化了什么 | 用户行为、业务规则和数据结果是否正确 |
| 依赖的文件与行号 | 静态引用在哪里 | 是否真实调用、走哪条运行路径、是否存在权限问题 |
| 测试文件只计数 | 改动里涉及多少测试文件 | 测试是否执行、断言覆盖什么、结果是否适用于当前代码 |
| 接受 / 标为违规 | 用户对结构问题作了什么处理 | 业务是否验收、问题是否修复并复核 |
| 按分支及稳定问题 ID 保存决定 | 同一问题不必每轮重复确认 | 新版本扩大了影响面时，旧决定是否仍然有效 |
| 独立的提交级 AI 叙述 | 给一次提交补充短说明 | 一个业务目标跨多次提交、多个项目的完整进展 |

当前源码有三个与产品目标直接相关的边界：

- **说明来源偏结构事实**：依赖提示由 `import` 等事实拼接，不含需求目标、行为前后对比和验收结果。[E1][E2]
- **已有 AI 叙述不是此页面的业务解释层**：现有提示词面向单次提交，要求 2–4 句说明，输入主要是分析结果和截断补丁。[E5]
- **“处理过”被表达成“审完了”**：结构结论只接收已决定的 ID。接受和标为违规都进入该集合，因此全部处理后可能出现“这个分支审完了”。这需要先纠正，不能在此基础上叠加更肯定的 AI 文案。[E3][E4]

### 1.3 产品的核心对象：业务变更项

不要继续以“一条新增依赖”为主要审查对象。增加 **业务变更项**，它代表一个可被用户理解、验证和决定的行为变化。

推荐的组织关系：

```text
任务目标
  └─ 业务变更项：一个用户场景 / 一条业务规则 / 一项对外契约
       ├─ 需求与约束
       ├─ 基准行为 → 当前行为
       ├─ 关键主逻辑与异常路径
       ├─ 对应的代码、配置与结构变化
       ├─ 测试和运行证据
       └─ 需要人的决定，以及决定适用的版本
```

**3 条结构变化不一定是 3 个业务变化，也不一定是 3 个风险。** 截图中的 3 条引用可能服务于同一个工作台目标，但必须先关联任务和实际代码，不能仅凭命名自动合并为既定事实。

地图继续保留，定位为“理解影响面与查看结构证据”的工具，而不是业务验收的替代品。

## 2. 角色与权限：AI 可以整理和执行，不能替人签字

| 角色/组件 | 负责 | 不应负责 |
| --- | --- | --- |
| 人 | 确认业务目标、范围、主逻辑、重要取舍；审查证据；最终接受结果 | 手工追踪每条 import、每次提交和所有聊天历史 |
| 实现 AI | 根据任务契约实现；报告变化、假设与缺口；按已有授权执行验证 | 自动把自己的解释标成事实，或把自己的实现认定为业务完成 |
| 审查说明服务 | 聚合事实；起草业务解释；定位风险线索和证据缺口 | 无证据宣称“权限安全”“没有回归”“可以合并” |
| IDE 的确定性规则 | 管理快照、证据引用、状态和门槛；拦截过期或缺失结果 | 单靠文件数和架构变化数推断业务正确性 |

第一版即使仍通过“复制修改要求”与外部 AI 协作，也要携带任务 ID、快照、约束和验收条件。后续有执行器适配能力时，再增加明确的“发给当前任务”。

**用户点击接受业务方案，不等于授权提交、合并、发布或生产操作。** 这些行为继续遵守现有工具权限和项目流程。

## 3. 两种审查模式：默认轻，关键处能深入

### 3.1 快看模式：先回答五个问题

默认首屏固定回答：

1. **为什么改**：当前任务目标，以及明确不做什么。
2. **改了什么业务行为**：用户或下游系统会感知到的变化。
3. **主逻辑有没有偏离**：关键规则、数据流和异常处理是否符合约定。
4. **目前证实到哪里**：结构事实、测试结果和业务验收分别是什么状态。
5. **我现在要做什么**：最重要的决定、补证据或复核动作。

默认每个业务变更项显示一个标题、少量摘要和一个主要动作。细节按需展开。**更详尽不等于让每张卡片默认展开成长文。**

建议的阅读目标：30 秒找回任务上下文；3 分钟识别本轮最重要的业务变化和未决问题。它们是待验证的产品目标，不是当前性能数据或对任意复杂任务的保证。

### 3.2 深审模式：沿业务路径查看，而不是只沿文件树查看

点开业务变更项后展示：

- 需求来源与已确认约束。
- 基准版本行为和当前版本行为。
- 主路径：入口、校验、核心规则、数据处理、输出。
- 异常路径：空值、权限失败、依赖失败、重复请求等实际相关分支。
- 关键代码片段、调用证据、测试断言与运行记录。
- 影响对象：用户、调用方、数据契约、依赖模块。

路径上的节点应能定位到真实符号或证据；不能把 import 关系图包装成已验证的运行时调用链。无法解析时，显示“路径待核验”。

## 4. AI 说明的内容组装：先补业务依据，再要求它写得详细

### 4.1 输入不是“整段 diff + 请详细描述”

| 输入 | 内容 | 缺失时的行为 |
| --- | --- | --- |
| 任务契约 | 要实现什么、不做什么、验收场景 | 只输出技术事实；提示补一句目标，不猜需求 |
| 已确认知识 | 业务术语、领域职责、规则、历史决策 | 显示未知；AI 草稿不得成为默认业务规范 |
| 版本化代码事实 | 基准与当前补丁、受影响符号、字段、配置和必要邻域 | 标明解析或读取范围；不能把截断外代码当成不存在 |
| 验证证据 | 命令、环境、实际断言、执行结果、对应快照 | 显示“未获取执行证据”，而不是“测试未执行”或“已通过” |
| 历史决定 | 用户认可的取舍、提出的修复要求和依据版本 | 仅复用仍适用的决定；影响面扩大时重新确认 |

第一次绑定任务不应要求填一份长 PRD。用户只需说一句目标，AI 起草“要做什么 / 不做什么 / 怎么算通过”，人修正关键项即可。已有需求文档可关联，但不能成为使用门槛。

### 4.2 业务变更项的固定内容

| 字段 | 写作要求 |
| --- | --- |
| 业务标题 | 主体 + 行为变化 + 业务对象；避免以类名开头 |
| 改动目的 | 关联已确认需求；没有需求时明确未知 |
| 之前 / 之后 | 分别引用基准和当前实现，避免仅凭提交标题猜“之前” |
| 主逻辑 | 说明关键输入、判断、输出；展示真正变化的节点 |
| 影响与风险 | 区分已发现问题、条件性风险、尚缺验证；写清触发条件和影响对象 |
| 验证情况 | 具体到验收场景与证据，不用“测试较充分”代替事实 |
| 待你决定 | 提出业务选择，并说明推荐项、理由和代价 |
| 证据与版本 | 代码/规则/报告引用，以及适用的快照和任务版本 |

### 4.3 每条陈述都有来源等级

- **代码事实**：例如某文件新增一个 import；由确定性采集结果提供。
- **业务约定**：例如用户确认“画像缺失不能阻断工作台”；记录确认者和任务版本。
- **AI 推断**：例如复用类型可能意味着统一卡片数据；必须保留“可能”和依据。
- **未知 / 未核验**：例如是否增加同步网络调用、失败时怎么处理。

不要只给整张卡片一个模糊“可信度 92%”。同一卡片可能包含确定事实、业务约定和未核验推断。

建议新增类型化输出，不直接把一段 Markdown 当审查结果保存。概念草图：

```json
{
  "taskID": "任务稳定标识",
  "snapshotID": "输入快照摘要",
  "contractVersion": "任务约定版本",
  "items": [{
    "id": "业务变更项稳定标识",
    "title": "业务标题",
    "claims": [{
      "text": "一条可单独核验的陈述",
      "basis": "code_fact | agreed_rule | inference | unknown",
      "evidenceIDs": [],
      "missingEvidence": []
    }],
    "acceptanceIDs": [],
    "decisionQuestion": "需要人决定什么"
  }]
}
```

渲染前检查结构、证据引用、仓库身份和版本。**证据 ID 存在，不代表它支持这句话。** 事实字段尽量直接来自规则；模型生成的语义解释，在人工或独立检查核验前仍是推断。

## 5. 关键功能设计

### 5.1 直接改造截图：先有一个诚实且有用的版本

#### 当前证据已经支持的卡片

**建议工作台新增对“AI 搭子”数据对象的引用**

- **实际变化**：`SuggestWorkbenchAssembler` 等 3 个文件新增对“AI 搭子”DTO 的引用，共 7 处。两个领域之前已经存在其他模块依赖。
- **目前能确定**：工作台的静态数据类型依赖扩大了。
- **尚不能确定**：是否改变用户可见字段、建议生成规则或运行时调用方式。
- **业务上为什么值得看**：如果这些对象承载建议卡片，复用可能让两处功能共享字段和状态定义；这是待核验的解释，不是已证实的功能变化。
- **需要你确认**：这些 DTO 是已认可的跨业务数据契约，还是“AI 搭子”的内部对象？若是内部对象，工作台对外输出应由谁定义？
- **下一步证据**：比较 DTO 字段、Assembler 映射、工作台对外返回和对应测试。

主要动作：**补充业务约定**。次要动作：查看证据、提出修改要求。

这比“3 个文件、7 处引用”更接近业务判断，又没有把缺失信息编成故事。

#### 其余两条应如何写

| 截图条目 | 可改成的说明主题 | 必须避免的越界推断 | 建议补齐的证据 |
| --- | --- | --- | --- |
| 工作台 → 画像 agentapi，5 处引用 | 工作台开始引用画像对外类型，需确认使用场景与缺失处理 | 不能仅凭引用就说新增远程调用、读取了画像或导致延迟 | 调用位置、所需字段、空值和失败分支、相关测试 |
| Controller agent → 工作台，1 处引用 | Controller 层新增工作台依赖，需确认入口职责 | 不能仅凭 import 就说新增接口、暴露了新能力或绕过鉴权 | 路由或入口差异、实际调用点、校验位置与权限测试 |

#### 业务上下文补齐后的表达目标

下面是**文案设计示例，不是截图分支事实**。假设用户确认的目标是：“建议工作台展示与 AI 搭子一致的建议卡片；没有画像时仍能返回基础建议。”

> **这轮要统一建议卡片的数据含义，而不是扩大用户可见范围。**
>
> 已确认目标：两处功能使用一致的建议文本与状态定义；画像缺失不阻断基础建议。
>
> 代码侧已发现：工作台新增 DTO 和画像 API 类型引用；这只能证明存在实现线索。
>
> 本轮重点：字段映射是否符合卡片约定，画像缺失分支是否保留，入口是否沿用原有用户范围校验。
>
> 当前缺口：还需要基准/当前行为对比及这三个场景的执行证据。

当证据采集完成后，才把“待核验”替换成具体结果。不能因为有一段流畅的业务说明，就让卡片自动变绿。

### 5.2 审查“主逻辑”，不能只审结构

新增行为变化扫描：条件表达式、默认值、计算公式、字段映射、状态迁移、鉴权/范围过滤、配置开关、异常处理和关键调用参数。

例如，同一个方法内把“仅当前用户”过滤删掉，可能完全没有新增依赖或接口。此时结构没变，业务风险却可能很高。该例仅用于说明检测能力要求，不是对截图分支的指控。

- 规则扫描产生“需要查看的线索”，不直接宣布发现业务漏洞。
- 沿已确认验收场景补充局部上下文，而不是每轮全仓解释。
- 测试、配置、脚本和文档不得全部按“其他”静默略过。
- 不支持的语言、反射、动态调用和截断范围应显式披露。
- 重要度由业务影响、变更类型、影响范围和证据缺口共同解释；引用多不等于风险大。

### 5.3 把“对不对”和“写得怎么样”分开回答

| 维度 | 用户要判断的内容 | 支撑证据 |
| --- | --- | --- |
| 需求一致性 | 做的是不是约定的事，有没有越界 | 任务契约与业务行为对照 |
| 主逻辑正确性 | 核心规则、状态和数据结果是否正确 | 基准/当前代码、验收场景、断言和运行记录 |
| 边界与兼容性 | 权限、失败处理、对外接口是否受影响 | 相关代码、契约检查、兼容性与权限测试 |
| 实现质量 | 是否引入不必要耦合、重复、复杂度或已测出的性能回退 | 结构事实、静态检查、基准结果与审查意见 |
| 验证完整性 | 哪些场景已经验证，哪些还没覆盖 | 明确的场景清单与逐项证据 |

不要用一个总分合并这些维度。测试通过只能支持已执行的断言；AI 写的测试也可能重复 AI 自己的错误理解。增加一个模型互审，可以帮助找问题，但不自动构成业务正确性的独立证明。

### 5.4 统一上下文：一份任务事实，两种视图

建议维护 **共享任务上下文**，包含：

- 目标、非目标、业务规则与验收场景。
- 关联仓库、工作树、分支和任务 ID。
- 人已接受的方案及其适用范围。
- 未决假设、修改要求、验证结果。
- 当前实现快照，以及最后审查的快照。

同一份内容生成两个投影：

- **给人看**：目标卡、主逻辑、决定记录、“自上次查看发生了什么”。
- **给 AI 用**：结构化目标、约束、证据引用、待办和验收条件。

不要复制整段聊天历史当作“共享上下文”。需要的是精炼、可追溯、版本一致的事实。

新增规则默认是草稿。用户确认后才进入生效约束。需求与实现冲突时，要记录偏离，不能把当前代码自动反写为“需求就是这样”。

界面提供“AI 本轮依据”：显示实际读取的任务版本、知识条目、快照和未读取范围。若接入外部 AI，则由适配器提供可核验回执；无法确认送达时明确显示“已导出，尚未确认读取”，不假装所有执行器都已同步。

### 5.5 版本与决定有效期：稳定 ID 只用于关联，不能自动继承批准

每个审查快照至少绑定：仓库/工作树身份、基准提交、当前提交、未提交内容摘要、任务版本和相关知识版本。

- 开启“含未提交”时，记录所包含的暂存、未暂存和未跟踪文件集合及内容摘要。
- 未保存的编辑器缓冲区若未采集，明确标为“不在此快照内”。
- 比较两端从同一组冻结输入读取，避免 AI 边写边读导致报告混用多个版本。
- AI 生成期间代码继续变化，可以保留旧报告，但显示“此说明对应上一快照”。不得把迟到结果覆盖到新快照。
- 接受记录保留稳定业务 ID，同时绑定证据与影响面指纹。
- 相关规则、字段、调用或影响面变化后转为“需重新确认”。无关文件变化不必让所有决定失效。
- “问题条目消失”不自动等于修复成功。需要重新验证原修改要求，而不是只看原 import 是否消失。

同时保留两个不同的基线：

1. **最后查看**：用于减少重复信息。
2. **最后批准**：用于判定哪些实现仍需审查。

查看过不等于认可过。

### 5.6 状态设计：阻止虚假的完成感

界面至少分开显示：**AI 执行状态、人的审查状态、验证状态、证据新鲜度**。

| 维度 | 示例状态 |
| --- | --- |
| AI 执行 | 未开始、执行中、等待输入、已交付、失败 |
| 人的审查 | 待确认、已接受当前方案、要求修改、待复核 |
| 验证 | 未获取结果、明确未执行、执行中、通过、失败、执行错误 |
| 新鲜度 | 当前快照、已过期、正在重新计算 |

关键显示规则：

- 结构项全部处理：显示“结构项已处理”，不显示“分支审完了”。
- 仍有修改要求：显示“有修改待完成/待复核”，不得收成看似成功的状态。
- 未获取测试记录：写“未获取测试执行证据”，不把它变成失败或通过。
- 测试全绿但缺验收场景：写“已执行的测试通过，业务验收仍有缺口”。
- 相关证据过期：取消“当前版本已验证”的表达。
- 满足约定门槛后：显示“当前快照满足约定验收条件”，而非“代码绝对正确”。

### 5.7 多项目：建设“待我处理”，而不是更多状态噪声

跨项目首页以 **项目 → 任务** 排列，不以聊天会话和提交数量排列。

每项只保留：目标一句话、当前阶段、上次查看后的业务变化、最高优先级问题和下一动作。以下是交互示意，不代表真实运行状态：

```text
项目 A · 建议卡片复用   → 等你确认数据契约
项目 B · 编辑器修复     → 新的测试失败需要处理
项目 C · 索引优化       → AI 仍在执行，当前无需操作
```

- 优先级可解释：先处理阻塞决定、已返回的验证失败、约束冲突和过期批准。
- 同一个业务问题聚合为一项；查看或刷新不重复通知。
- 只在需要决定、失败或达到可审查里程碑时打扰人，不逐次播报 AI 改文件。
- 切回项目时给“上下文恢复卡”：目标、已定事项、新增变化、未解决问题。
- 未接入执行器时，显示“任务进度未知”，不能从文件变化推断 AI 仍在正常工作。
- 缓存、队列、决定和模型请求都必须按仓库/工作树/任务隔离；不能仅用分支名。

### 5.8 技术落地：复用当前能力，不另建一套孤立的系统

| 当前可复用组件 | 方案中的职责 | 必须增加的部分 |
| --- | --- | --- |
| 结构事实、结构差异、问题生成 [E1][E2] | 提供确定性的结构证据 | 行为变化线索、覆盖范围和未知项 |
| 当前结构结论与卡片 [E3][E4] | 继续保留地图入口和证据定位 | 安全的结论规则；业务摘要/展开详情；明显的版本标签 |
| AIReview 的 Provider、脱敏与配置 [E5] | 复用模型调用通道 | 独立的业务解释 schema、提示词版本和输出校验 |
| Wiki 草稿/确认、来源与领域关联 [E6] | 复用业务知识与人工确认机制 | 任务级检索、规则适用范围和来源新鲜度 |
| 结构决定持久化 [E4] | 兼容已有人的判断 | 决策理由、证据指纹、状态迁移和过期判定 |
| 多根 SourceControlWorkspace [E7] | 获取正确的仓库、分支和变更 | 任务身份、按工作树隔离的审查状态、跨项目注意事项聚合 |

建议的新增职责，名称为设计草案，尚未创建这些代码文件：

- `TaskContractStore`：保存目标、约束、验收和确认历史。
- `ReviewSnapshotBuilder`：冻结本轮分析输入，生成可追溯版本标识。
- `BusinessReviewService`：合并任务、事实和知识，调用模型生成业务说明。
- `ReviewEvidenceStore`：保存代码、静态检查和执行报告的证据索引。
- `ReviewDecisionStore`：管理业务决定、修改要求和复核状态。
- `ReviewAttentionCoordinator`：跨项目汇总真正需要人的事项。

第一版可用本地类型化 JSON 与已有 Wiki 文件存储，不先引入数据库或图数据库。任务契约可选择纳入版本管理；缓存、原始执行日志和运行态应默认留在本机。写入采用可检查错误的原子操作。

**不要直接把现有提交说明提示词从“2–4 句”改成“写详细”。** 新增业务解释服务，复用通道；提交说明保持原职责，减少改动扩散。

### 5.9 成本、失败和数据边界

- 先显示本地事实，再异步补业务说明；模型不可用时保留可用的事实卡。
- 按任务里程碑或手动刷新生成，不在每次按键后调用模型。
- 缓存键纳入快照、任务、相关知识、模型、提示词和 schema 版本。
- 大分支先划分业务变更项，再读取局部上下文；对未读取文件与截断明确提示。
- 不从成本不足推出“没有问题”；未分析范围保持可见。
- 默认尊重现有 AI 开关和 Provider 配置，发送前脱敏并按授权范围取代码。
- 仓库文档、注释和模型输出都是数据。它们不能覆盖用户规则，也不能自动触发工具执行。
- 对错误 JSON、失效证据、模型超时和任务取消，都保留清晰状态，不降级成成功。

## 6. 交互设计：保留简洁入口，减少用户搬运信息

### 6.1 当前页面的建议布局

```text
项目 / 任务 / 当前分支     对比基准     快照与新鲜度

这轮要做什么：一句已确认的任务目标
当前结论：哪些变化已证实，哪些仍缺证据

[业务变化]  [待我决定]  [验证记录]  [结构地图]

业务变更卡
  标题：用户或调用方会感知到的变化
  之前 → 之后（没有依据就写待核验）
  主逻辑：只突出变化节点
  证据：已证实 / 推断 / 未核验
  你要决定：选择、理由与后果
  [主要动作] [查看详情]

展开详情：关键代码 / 需求来源 / 测试断言 / 影响关系
```

对于当前截图，在任务未绑定、执行证据未接入时，顶部可先写：

> **发现 3 条结构变化；业务目标尚未绑定。**
> 暂未获取测试执行证据。请先说明这轮要实现什么，再判断变化是否符合目标。

这比让模型编造一个看起来专业的完成总结更符合“让人心里有底”。

### 6.2 动作必须符合用户正在做的判断

| 动作 | 含义 | 后续 |
| --- | --- | --- |
| 接受当前方案 | 认可这项业务取舍，不代表整体完成 | 保存适用范围、依据与快照 |
| 要求修改 | 实现不符合规则，或用户选择另一方案 | 生成带业务原因和验收条件的修改要求 |
| 补证据 | 当前无法判断，不等于违规 | 补读代码或执行获准的验证 |
| 修正理解 | AI 对业务目标或影响的解释错了 | 修正任务事实，重新生成受影响说明 |

“标为违规”可保留为深层结构操作，但不应成为用户表达“我还不知道”的唯一替代选项。

发送给 AI 的内容至少包含：问题、业务规则、关联证据、允许的修改范围、不能改变什么、如何验收。不能只发送“删掉这 7 条引用”。

### 6.3 一次完整的协作流程

1. 人用一句话声明任务，确认关键约束与验收场景。
2. AI 基于明确版本开始实现；IDE 记录任务与仓库绑定。
3. AI 到达可审查节点，IDE 冻结快照并生成业务变更项。
4. 人先看摘要和主逻辑，对关键选择作决定。
5. 修改要求携带约束与证据回到该任务。
6. AI 提交新结果；IDE 比较相关变化并重新验证原要求。
7. 人复核当前快照，系统保存有效决定与剩余缺口。

业务解释出错时，允许就地修正；不要逼用户通过编辑源码或新建聊天来纠正解释。

## 7. 交付范围、验收与相关文档

### 7.1 推荐实施顺序

不先给固定工期：工程量取决于执行器、测试报告和语言分析的接入程度。按四个可独立验收的里程碑推进。

| 里程碑 | 交付内容 | 验收结果 |
| --- | --- | --- |
| M0：先纠正完成感 | 限定结构结论；违规保持待解决；区分测试文件和执行证据；显示快照 | 不再把“处理了结构项”表达成“业务已审完” |
| M1：业务卡片最小版本 | 一句话任务契约；检索已确认 Wiki；确定性事实 + 结构化业务解释；展开证据；决定带版本 | 一个真实分支能看清目标、实现线索、未知项和待决定事项 |
| M2：主逻辑与验证 | 行为变化线索；前后路径；验收场景与实际测试报告；修改后的定向复核 | 用户能判断主规则是否符合约定，并看清验证缺口 |
| M3：多项目上下文 | 上次查看/批准双基线；任务恢复卡；跨项目待处理；执行器上下文回执 | 切换项目时无需重读历史，不串仓、不重复打扰 |

**第一期明确不做**：全自动合并、宣称完整理解全仓、任意语言的完备调用图、用总分代替审查、多个模型轮流“盖章”，或为使用产品先要求补齐整套业务文档。

### 7.2 必须验证的样例

| 场景 | 期望 |
| --- | --- |
| 只有 import 变化，没有调用证据 | 不声称新增运行路径、远程调用或业务能力 |
| 方法内部改了关键规则，结构关系不变 | 仍能进入行为审查，不以“结构没变”结束 |
| 有 13 个测试文件，但没有执行结果 | 显示未获取结果，不显示通过或覆盖率 |
| 结构项全部标为违规 | 仍显示待修改，不能宣布完成 |
| 用户接受后，同一依赖扩大了字段或影响范围 | 相应决定失效，要求重新确认 |
| AI 在说明生成期间继续改文件 | 迟到报告不覆盖当前快照结论 |
| 两个仓库、两个工作树存在同名分支 | 任务、证据、决定和缓存不串用 |
| 文档已确认，但所依据代码发生变化 | 标记新鲜度问题，不把旧知识当成当前实现 |
| 测试通过，但需求中的异常场景未验证 | 保留验收缺口 |
| 模型输出虚构引用、错误格式或超时 | 拒绝错误内容或保留事实降级，不伪造完成 |
| 原结构问题消失，但业务修改要求未满足 | 维持待复核，不能自动关闭 |
| 用户查看过但未批准，随后切换项目 | 恢复卡可减少重复信息，审查仍然待办 |

建议先选一组经人工复核的真实变更作为基准集，再衡量业务解释准确性、重大风险漏报、重复提醒和恢复上下文耗时。不要先拍一个“AI 正确率”数字。

### 7.3 成功标准

- 用户能解释“AI 这轮要做什么、主逻辑怎么变、哪些已验证、还需要我做什么”。
- 每个决定都能追溯到业务依据和对应实现版本。
- 信息缺失、冲突或过期时，产品清楚承认边界。
- AI 接收的有效约束与用户界面展示的约束来自同一份任务事实。
- 多项目切换后，用户只需阅读增量信息，而不是重新构建完整背景。
