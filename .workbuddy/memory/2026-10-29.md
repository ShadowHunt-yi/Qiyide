## 修复启动时的两类 Auto Layout 告警

用户上一轮报「报错」，实际输出是 QiyideDev 启动时的两类 AppKit 告警（无崩溃、构建 0 error）。

### 1. `NSLayoutConstraint ... constant that exceeds internal limits`

来源：`CodeEditSplitViewController.makeInspector` 里
`inspector.maximumThickness = .greatestFiniteMagnitude`（1.8e308）。
AppKit 把它换成布局约束后常量超出内部上限。

修：删除该行，用 API 默认值（本来就是「不限宽度」）。
定位方式：全局搜 `greatestFiniteMagnitude` + 逐项 A/B 重建验证。

### 2. `NSToolbarItem -> view was automatically measured ... zero height or width`

来源有两处：
- 5 个 toolbar item 用裸 `NSHostingView` 作 view，没有给尺寸；
  AppKit 做第一次自动测量时读的是 view 当前 frame（0×0）→ 歧义尺寸。
- `NotificationToolbarItem` 在无通知时 `if` 没有 else，隐式 EmptyView → 0×0。

修：
- 新增 `CodeEditWindowController.toolbarHostingView(_:minWidth:)`：
  `sizingOptions = [.intrinsicContentSize]`、`translatesAutoresizingMaskIntoConstraints = false`、
  可选 `minWidth` 约束，并在交给 `NSToolbarItem` **之前**塞入非零 frame
  （宽高取内容 ideal，量不出来兜底 22 / 1）。
- 通知项 else 分支补 `Color.clear.frame(width: 0, height: 22)`。
- 高度**没有**统一写死 22：实测 ActivityViewer 理想高度 36、BranchPicker 17，
  写死 22 会裁内容。按内容真实尺寸走即可，警告消除的关键是非零初始 frame。

### 验证
同一命令启动 App 打开 saas 仓库，stderr 从 6 条告警 → **0 条**。
构建 build_exit=0，`error:` 计数 0。已重新打包 build/QiyideDev.app。

### 注意
- 沙箱内 `log show` 被拒（`Cannot run while sandboxed`）、`ps` 被拒，运行时日志只能靠
  直接执行 `build/Build/Products/Debug/Qiyide.app/Contents/MacOS/Qiyide <repo>` 抓 stderr。
- `lldb --batch` 加符号断点在沙箱里挂住，未能拿到栈；改用 A/B 重建定位更快。

## Java / Python 语法高亮失效（三层根因叠加）

用户报「Java 和 Python 都没有正常的语法解析与高亮」。逐层排查后发现是三个独立问题
叠加，任何一个都会让高亮整条链路断掉：

### 1. `CaptureName.fromString` 不认点号形式的 capture 名（最关键）
tree-sitter 的 capture 名多是 `function.method`、`type.builtin`、`variable.parameter`、
`punctuation.bracket` 这类 `category.subcategory` 形式，而映射表只认单词形式
（`method`、`type`、`keyword`…），带点号的全部落到 `default: return nil` 被丢弃。
表现就是「解析正常、查询正常，但一个字都没上色」。
修：先精确匹配，失败后按点号从右往左逐段尝试（`function.method` 先试 `method`），
并补齐 `operator/attribute/constant/exception/namespace/field/label/punctuation`
等常见词的兜底归类。文件：`CodeEditSourceEditor/Enums/CaptureName.swift`。

### 2. 初始解析与查询在 executor 队列里互相等
`TreeSitterClient.setUp` 的解析是 `reset` 优先级、高亮查询是 `access` 优先级。
`canTaskExec` 规定 access 任务必须等队列里的 reset 任务跑完；而查询又排在解析
后面。解析一旦排队等待（大文件几百毫秒），两者就死锁，高亮永远不出现。
单文件小样例之所以「正常」，是解析足够快、在查询前就跑完了——这掩盖了问题。
修：初始解析不再走 executor 队列，直接同步跑完（几十到几百毫秒）；
并在解析完成后发 `setUpFinishedNotification`，Highlighter 收到后补一轮查询。
文件：`TreeSitterClient.swift`、`Highlighter.swift`。

### 3. Highlighter 创建后从不主动发起首轮查询
`HighlightProviderState.init` 只调 `setUp`，不调 `invalidate`；
`styleContainer.documentLength` 只在 `setProviders` 里更新；
`VisibleRangeProvider` 只监听 frame/bounds 变化。在「文本先写入、Highlighter 后创建」
的路径下（`TextViewController.setText` 就是这个顺序），第一轮查询没有任何触发点。
修：`setText` 里先 `layoutManager.layoutLines()`（保证 `visibleTextRange` 有值）
再建 Highlighter；`Highlighter.init` 末尾主动调一次 `visibleRangeProvider.visibleTextChanged()`
并监听 setUp 完成通知。

### 顺带修复：provider 身份不稳定
`CodeFileView` 的 `highlightProviders` 原在 `init` 里组装成普通属性，而
`TreeSitterClient` 由 `@State` 的初始化表达式创建——SwiftUI 每次重建 View 都新建实例，
`Highlighter.setProviders` 按 `ObjectIdentifier` 判定「provider 全变了」，整条高亮管线
被反复拆掉重建。改：provider 全部由 `@State` 持有，数组在 body 里现算（元素不变）。

### 验证
workspace 模式打开 saas 仓库的真实文件（探针统计 `NSTextStorage` 的前景色分布）：
- `ChatLatencyVerification.java`（19035 字符）→ **6 种颜色**，覆盖全文
- `patch-publication.py`（10720 字符）→ **5 种颜色**，覆盖全文
修复前两者都是 1 种颜色（纯黑，无任何高亮）。

### 遗留（未修，不在本次范围）
`LanguageQueryDiagnostics`（Debug 启动自检）显示 **8 个语言的查询编译失败**：
cSharp / dockerfile / go / haskell / julia / perl / **swift** / verilog。
错误是 `nodeType(N)`——`.scm` 查询文件与 binary parser 版本不匹配（`highlights.scm`
来自 nvim-treesitter 较新版本）。这些语言目前完全没有高亮，且 `TreeSitterModel.query`
把错误吞成 `nil`、无任何日志。建议后续做「逐条过滤可编译规则」的降级，
或把 `.scm` 对齐 parser 版本。**Swift 是本项目主语言，优先级高。**

## 语法高亮配色细化（方法/参数不再同色）

用户反馈「方法和参数都是同一个颜色」。根因是 **`EditorTheme.mapCapture` 把
`function`/`method`/`parameter`/`property`/`variable` 全部映射到同一个 `variables`
颜色槽**，而主题只有 10 个颜色槽位、tree-sitter 的语义类有 20 多个——必然挤在一起。

### 三层改造

**1. `CaptureName` 扩充语义粒度**（+7 个 case）
`operator`、`punctuation`、`decorator`、`constant`、`namespace`、`field`、`escape`。
`fromString` 的点号拆分保留 subcategory 语义（`function.method`→method、
`variable.parameter`→parameter），常见词做精确归类。

**2. `EditorTheme` 扩充颜色槽位**（+8 个）
`functions`、`methods`、`properties`、`parameters`、`constants`、`operators`、
`punctuation`、`decorators`。`mapCapture` 按语义精确映射，不再混色。
init 的新参数带默认值、回退到最接近的旧槽位 → 旧主题文件不必改动。
`Theme.EditorColors` 加自定义 `init(from:)` 用 `decodeIfPresent`，缺失字段自动回退。

**3. 内置主题补语义色板**
18 个 `.cetheme` 全部补上新槽位。分两套按背景亮度自动选：
- 浅色：函数/方法 #4271AE 蓝、参数 #AA5D00 橙+斜体、属性 #3F8087 青绿、
  常量 #804FB8 紫、运算符 #AD3DA4 紫红、标点 #555555 灰、装饰器 #947100 金
- 深色：函数/方法 #FFB86C 橙、参数 #E5C07B 浅黄+斜体、属性 #B281EB 紫、
  常量 #D9C97C 黄、运算符 #FF7AB2 粉、标点 #7F8C98 灰、装饰器 #CC9768 橙棕

**踩过的坑**：一开始用「角色→已有槽位」的借用规则给主题补色，在 `Basic` 这类
极简主题（只有 5 种颜色）上失效——commands 和 values 本身同色，借出来的新槽位
也同色。改成统一语义色板后才真正解决。

### 验证
探针打印 14 个语义类的映射，全部不同色（method/function 共享蓝是主流做法）：
```
method→#4271ae  parameter→#aa5d00(斜体)  property→#3f8087
constant→#804fb8  operator→#ad3da4  decorator→#947100
type→#02638c  string→#b4261a  comment→#008f00  punctuation→#555555
```
Java 文件实际渲染颜色种类 6→8，分布更均匀。

## 「整篇被染成一种颜色」的真正根因：辅助 query 被误判为高亮

用户反馈截图里整屏只有一个蓝色（Solarized Light 的 type 色）。
**这不是配色问题，是 capture 误判**——上一轮为了让 `function.method` 能被识别，
加了「按点号从右往左逐段尝试」的宽松匹配，结果把 nvim-treesitter 的**辅助 query**
也当成了高亮 capture。

### 证据（打印实际 capture 名与范围）
```
definition.class@350+1035     ← 覆盖 1035 字符，末段 "class" 命中 .type
local.definition.type@369+13  ← "type" 命中 .type
local.scope@0+1386            ← 覆盖整个文件
fold@79+51  indent.begin@407+978  injection.content@726+60
```
`definition.*` / `local.*` / `fold` / `indent.*` / `injection.*` 是语法包里
**服务于导航、折叠、缩进、语法注入**的 query，覆盖的是整段代码而不是词法单元。
`definition.class` 覆盖整个 class 体 → 整块被染成 type 色 → 用户看到「全蓝」。

### 修复
`CaptureName.fromString` 在点号拆分**之前**先看首段，命中
`definition / local / fold / indent / injection / spell` 就返回 nil。
（注意不能无差别排除 `text.*`，那是 Markdown 的有效高亮。）

### 验证（用户真实路径：打开文件夹 → 文件树点开 → tab 显示）
文件 `AgentMemoryVO.java`（1386 字符），修复前后：

| 类型 | 修复前 | 修复后 | 文件实际构成 |
|---|---|---|---|
| comment 注释 | 135 | **512** | 512 |
| type 类型 | 1035 | **102** | 60+ |
| keyword 关键字 | 31 | **154** | 127+ |
| 颜色种类 | 5 | **8** | — |

### 两个方法论教训
1. **只看「颜色种类」不够，必须看分布比例**。上一轮单文件验证得到 6 种颜色就
   判定通过，但没检查 `type` 是否覆盖了不该覆盖的大段文本——同样的 bug 在
   小 class 文件上不明显，在 80 行的 VO 类上就吞掉 75% 的字符。
2. **验证必须在用户实际使用的路径上做**。之前一直用命令行
   `Qiyide <file>` 打开单文件窗口，而用户用的是「打开文件夹 → 文件树点开」。
   主窗口路径走 `editorManager.activeEditor.openTab`，与单文件窗口不是同一入口。
   后续复现主窗口路径的做法：在 `WorkspaceView` 的 `.onAppear` 里按环境变量
   调用 `activeEditor.openTab(file:)`（诊断完记得删）。

### 算法关键点（经 Python 同仓库验证）
1. **必须按 depth-2 聚合后代再评分**。域内的类几乎都在子包里
   （`agent/customerservice/core/*`），本层目录往往一个 `.java` 都没有，
   直接按目录统计会把整个域漏掉。
2. **技术层降权 0.5**：`db/mapper/domain/entity/repository/dao/dto/enums/...`
   命中就打对折。不降权时 `service/db/portrait`（237 类）会以 0.932 分压过真正的
   业务域 `service/portrait`（0.75）。
3. **中文词频是很强的信号**：实测 `画像` 1460、`建议` 540、`客服` 257、`搭子` 217 次。
   `@author` 反而完全不可用（仅 5 处且是 `DongBoot`/`guer`/`Administrator` 模板值）。
4. **人名取 git author**：4 位真实开发者（wangshizun1 99、liangzhenqi1 56…）。

## 阶段 2：多视角投影（已实现）

### 新增文件
- `Models/ViewSpec.swift`：`ViewAxis`(5) / `SharedDependencyPolicy`(4) /
  `ViewGranularity`(3) / `ViewEdgeSemantics`(5) + 5 个预设 + `ViewSpecStore`
  （自定义视角存 `.qiyide/wiki/viewspec/*.json`，可随仓库分享）。
- `Service/ViewProjector.swift`：按规格投影，只读、不改原模型，
  节点 id 加 `view:` 前缀避免混淆。

### 五个预设视角
| 视角 | 分层轴 | 共享依赖 | 边 |
|---|---|---|---|
| 业务能力图 | business | hoist（上提基建层） | dependency |
| 技术架构图 | technical | keep（作为代码并列） | dependency |
| 变更影响图 | impact | duplicate | propagation |
| 数据契约图 | data | hide | dataFlow |
| 团队归属图 | ownership | keep | ownership |

### 关键实现细节
1. **技术分层判定顺序必须是「数据 → 入口 → 业务 → 领域 → 兜底」**。
   `service/db` 既含 service 又含 db，先判 db 才能避免整片持久化代码被算进业务层。
2. **投影视图只读**。`MindMapView` 增加 `displayGraph` / `isReadOnly`：
   投影视图的节点 id 带 `view:` 前缀，编辑它们改不到原模型，所以右键只留查看与展开。
3. **空层不画**：技术视角下某层没有节点就跳过，避免出现四个空壳层。
4. **数据视角兜底**：没有命中任何数据层包时退回业务视图，避免出空图。

### UI
- 窗口顶部新增视角 `Picker`（建模视图 + 5 预设 + 自定义）。
- 「自定义视角」按钮 → 表单（名称/分层轴/粒度/共享策略/边语义）→ 保存并应用。

## 阶段 3：知识库生成（已实现）

### 新增文件
- `Service/WikiDomainSeeding.swift`：`seed(graph:into:)`，把锁定的领域模型
  逐域落成知识草稿。

### 设计取舍
1. **用模板不用模型**：模块清单/类数/负责人/判定依据本来就是结构化数据，
   拼 Markdown 比让模型复述更准、不会编造；且没配模型时也能用。
   需要 AI 补全时走已有的 `WikiCurationRunner`（「AI 整理」菜单），不重复调用。
2. **生成的是草稿**（`status = .draft`，`generatedBy = "领域建模"`），
   正文末尾固定留「设计意图（待补充）」三问：解决什么问题 / 边界为何在此 /
   改动要同时关注谁。模型写不出设计意图，只有人知道。
3. **同名条目直接跳过**，不覆盖——人工写过的内容不能被重新生成冲掉。
4. `WikiStore` 是 `@MainActor`，`seed` 标 `@MainActor`；只写几个文件，主线程足够。

### UI
- 窗口工具条「生成知识库」按钮（仅锁定后出现）。
- 生成后显示绿色提示条：已生成 N 条 / 跳过 M 条同名 / 去知识图谱确认。
