## 修复：历史记录时间全部显示「现在」（10:32-10:38）

根因：`GitClient+CommitHistory` 取 `%aD`（RFC 2822，英文月日），却用
`DateFormatter(locale: Locale.current)` 解析；zh_CN 环境下 "Thu, 11 Jun 2026 ..." 必然解析失败，
失败后回退 `Date()`，而 `CommitListItemView` 用 `relativeStringToNow()` 展示 → 全部变成「刚刚/现在」。
实测确认：zh_CN + "EEE, dd MMM yyyy HH:mm:ss Z" 解析该串返回 nil。

修复：
1. CommitHistory：改用 `%aI`（严格 ISO 8601，不受 log.date 配置影响）+ ISO8601DateFormatter
   （withInternetDateTime，兼容带毫秒与纯时间戳）；解析失败返回 nil → `.distantPast`，
   不再用当前时间伪装。
2. GitClient+Blame 行历史：`--date=short` 原拼在 `--pretty=format:` 值内部，既不生效
   （%ad 输出长格式）又把字面量追加到摘要；改为独立参数。
3. GitClient+Stash：`--date=local` 日期形如 "Tue Oct 27 10:33:30 2026"，同样 Locale.current 解析失败
   → 条目被静默丢弃（stash 列表为空）；改 en_US_POSIX。
4. GitBlameLine.dateFormatter 固定 en_US_POSIX（数字日期不随区域变化）。

验证：三文件语法检查通过；实测新命令输出 `2026-10-10T11:07:46+08:00`、行历史 `2026-06-11`；
Swift 片段验证旧解析返回 nil、新解析正确；`./scripts/build.sh` 成功（10:37）。

通用教训：解析 git 输出的日期必须用 POSIX locale 或机器可读格式（%aI），
禁止用 Locale.current，也不要用 Date() 兜底。

## blame 标注真正根因（16:24-16:45）

用户提供日志：`blame 标注已安装 0/10 行`（取到数据但一条没装上），随后一条「已关闭」。

根因（实测）：`NSString.enumerateSubstrings(.byLines)` 返回的区间**不含行终止符**：
"abc\ndef" → {0,3}、{4,3}，换行符在 location+length 处。
而锚点按 `location + length - 1` 计算 → 拿到 'c'/'f'，随后「锚点必须是换行符」的守卫
对每一行都不成立 → 全部 continue。「末行不吞字符」那次修复引入的回归。

修复：锚点改 `location + length`；CRLF 锚在 LF；末行无换行仍跳过。
等价脚本验证：LF 三行→3 锚点；无尾换行→跳过最后一行；CRLF→锚在 LF。

## 2026-10-28 「模型返回了空内容」根因与修复

现象：审查窗口里点生成 → 立刻（约 300ms）红字「模型返回了空内容」。

### 修掉的真实缺陷
1. `WikiStore.applyDraft` 的 update 是纯 append → 同一模块跑 N 轮累积 N 段「补充」。
   加 `WikiDraft.MergeMode{append, replace}`，建档用 replace，并保留人以「**补充（」开头的段落。
2. `WikiInsightStore` 的 mtime 容差原本 1 秒 → 同一秒内保存两次会漏判。收紧到 0.001。
3. `distribute` 按文件数截断会拆散知识单元 → 改为 `selectUnits`：单元要么整块进入、要么整轮跳过。
4. `WikiRepoIngest.scan` 的固定三段路径聚类 → 换成内聚切分（同仓库三种粒度并存）。

### 踩坑
- `NSURL.resourceValues` 会对同一 URL 实例缓存属性：测试里复用同一个 URL 变量会读到旧 size，
  误判成「文件改了仍命中」。测试要每次新建 `URL(fileURLWithPath:)`；生产代码每次 appending 无此问题。
- 破环策略：优先「出边最少」反而违规翻倍（144 vs 64），必须优先「被依赖多、依赖少」。
- Swift `compactMap` 闭包返回 nil 需显式标 `-> T?`，否则类型推断成非可选报错。
- 类内 `static let default` 与关键字冲突，改名 `standard`；`Options.default` 一并替换。

## 2026-10-28 建档卡死：布局在写入循环里被反复重算

现象：用户点「开始建档」后界面长时间无响应。进程还活着，无崩溃报告。

定位（sample 63735）：
```
WikiCurationRunner.runRound() :470
 └ WikiStore.applyDraft()  :308
   └ WikiStore.reload()    :72
     └ WikiStore.rebuildGraph() :170
       └ WikiLayout.compute() WikiGraph.swift:115
```
270 个主线程样本全部落在这条链上。

根因两处，叠加放大：
1. **每写一条条目就 applyDraft → reload → rebuildGraph → 力导向布局**。
   一轮十几条 = 十几次全图布局，全在主线程。
2. **WikiLayout.compute 全程用 [String: CGPoint]**：每帧上万次字符串哈希查找，
   159 节点 837 边要一秒多（Debug 更慢）。

修复：
- `WikiStore.applyDraft(_:generatedBy:sources:refresh:)` 新增 `refresh` 参数，
  false 时只写文件不重建内存；Runner 写入循环用 `refresh:false`，本轮结束 `store.reload()` 一次。
  循环内用本地 `knownTitles` 判断 create/update（因为内存没刷新）。
- `WikiStore.save(_ entries: [WikiEntry])` 批量保存；`reconcileRelations` 改为收集后一次 save
  （原来上百个条目逐条 save = 上百次重扫 + 布局）。
- `WikiLayout.compute` 用索引数组重写：id→下标只建一次，斥力/引力/位移全在 [Double] 上做。
  另有规模降级：≤120 节点 320 次迭代，≤300 160 次，≤600 80 次，更多 40 次。
  确定性不变（不引入随机数，两次坐标逐位一致，有断言）。
- `WikiRepoIngest.scan` 移到 `Task.detached`，避免点「开始」时先僵 1–2 秒。

实测：159 节点 837 边单次布局 **7ms**（-O；Debug 约 50ms）；12 条延迟写入 13ms + 一次 reload 4ms。

顺带补的诊断能力：
- 理解阶段每批结束、写入每条之后都 `job.save`。之前只在轮末保存，
  卡死时 `callsUsed` / `round` 全归零，看不出已经花了多少调用、跑到哪。

**用户实际的建档跑在 `saas-plus-ai-platform`，不在 CodeEdit**：
`.qide/wiki/.insights.json` 已有 237 个文件的结论（质量不错），但一条 .md 都没落盘，
job 里 round=0 / callsUsed=0。重跑时这 237 条会被直接复用，不重复付费。

## 2026-10-28 排查「又崩溃了」：不是崩溃，是进度不落盘

证据链：
- 进程存活，无新崩溃报告；`sample` 2 秒 1739 个样本，主线程全在 `_DPSBlockUntilNextEventMatchingListInMode`（空闲）。
- 全部样本里只有 1 个落在 `WikiModelClient.callJSON` → 说明几乎全在等网络，CPU 不忙。
- cc-switch `proxy_request_logs`：近 15 分钟 149 次请求、全部 200、单次 7–13 秒。
→ 任务一直在正常跑，只是**界面和磁盘都没有任何进度信号**。

根因：`WikiModelClient.run` 要等**整组批次全部返回**才把结果交给调用方，
而 `insights.save` / `job.save` / `progress` 更新都挂在「整组之后」。
所以几十批、几分钟内，`insights.json` 的 mtime 和面板数字一动不动。

修复：
- `schedule` 增加 `onResult` 回调，`run` / `runRelate` 透传 `onOutcome`。
- Runner 新增轮内状态（activeInsights / activeResolved / understoodCount / totalBatches / doneBatches），
  `consumeUnderstanding(_:root:model:)` 每批完成即：累加 callsUsed、写 insights 缓存、落盘 job、刷新 detail 与 progress。
  用 `consumedBatches` 按批次 id 去重——回调与 `run` 返回值都会送同一个 outcome。
- 顺带修短标题：知识单元名是仓库相对路径，Java 项目 155 字符，
  列表 `lineLimit(1)` 只显示开头 `saas-plus-ai-platform-app/src/...`，最关键的末段被截掉。
  新增 `WikiEntry.displayTitle`（末两段）、`WikiNode.label`；图谱 `shortTitle` 从 `prefix(12)` 改为取末段。

实测（saas-plus-ai-platform）：
- 全仓 2666 个源码文件；round 1 产出 **59 条草稿**、callsUsed 136、failures 1。
- 条目质量高，典型如「会话调用链分页刻意不查询 state_json，以兼容旧库尚未迁移该字段」。
- 粒度：单文件级 26 / 目录级 33（Java 项目 Mapper、Entity 多为单文件单元）。
- 按每轮 240 文件估算需 11 轮，超过 `maxCallsTotal=800` 安全阀会自动停。

教训：长任务只要有一个「整组返回才落盘」的瓶颈，用户就一定会认为它挂了。
进度必须在最小完成单元上落盘。
