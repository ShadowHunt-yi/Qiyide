# 2026-11-02 · 知识库与领域建模合并：阶段 1（数据打标）

用户的判断是「领域建模和知识图谱有点分离」，方向上我同意，但根因不是窗口多，
而是**同一个「域」有三套互不相认的身份**：

| 层 | 身份 | 存储 |
|---|---|---|
| 领域建模 | `MindNode.id = "domain:service/portrait"` | `domains.locked.json` |
| 架构视图 | `WikiDomain.name`（自由文本，无 id） | `architecture.json` |
| 知识条目 | **没有域字段**，只有 `tags: ["domain","领域"]` | `*.md` |

方案：以 `MindGraph` 为唯一事实源，`WikiEntry.domains` 与
`WikiDomain.domainID` 都指向 `DomainID`（即 `MindNode.id`）。
四阶段：① 打标 ② 合窗 ③ 流水线+体检 ④ 入口收敛。本次只做阶段 1。

## 已落地（阶段 1）

- `WikiEntry.domains: [String]`，frontmatter 键 `domains:`（也兼容手写 `domain:`），
  缺失即空数组，老条目零改动可用。
- `WikiStore`：新增 `entriesByDomain` 索引 + `entries(inDomain:)` / `unassignedEntries` /
  `taggedDomainIDs`。
- `WikiDomainSeeding`：生成时写 `domains = [domain.id]`，正文加「归属」小节；
  跳过规则从「同名即跳过」改成三分支（同域同名 / 无标记 / 被别的域占用并给警告）——
  否则两个域同标题时会互相顶掉且无人知晓。
- `WikiDomainBackfill`（新）：只算不写的归属报告 + `apply` 批量补写。
- `DomainBackfillSheet`（新）：建模窗口「域归属」按钮打开，列出空缺域/可归属/多义/无归属。

- 验证入口加「打标自检」：frontmatter 往返 + 报告 + 可选写入路径。

## 关键算法：归属判定优先级（被真实数据逼出来的）

第一版按「每个域是否有任一 source 命中」判，真实仓库 240 条上得到
**111 可归属 / 110 多义**——大量本该唯一的条目被判成歧义。原因是兜底域
（按一级包聚合的 `agent`、`service`）会命中所有子路径。

改为三条优先级后 **221 / 0 / 19 / 0**：

1. **同一路径上靠前的业务段优先**：`agent/service/X.java` 同时含 `agent` 与 `service`，
   它属于 `agent` 产品线，`service` 只是子目录名；
2. **同起点时长键优先**：`service/portrait` 胜过 `service`，兜底域抢不走具体域认领的路径；
3. **不同 source 命中不同域才算多义**：这才是真正的跨域条目。

匹配必须按「段」而非子串：`agent/suggest` 不能命中 `agent/suggestion`。

### 打标未完成时的显示（重要）

240 条全没打标时，域下面的计数全是 0。第一版直接把 0 渲染成橙色的「缺口」，

`ImageRenderer` 画不了带原生控件的界面——`Button`/`Picker`/`HSplitView` 会被整块

入口：`QIYIDE_VERIFY_WIKI=<repo>`，可选 `QIYIDE_VERIFY_WIKI_OUT` 指定输出。

## 阶段 3：流水线状态条 + 一致性体检

- `WikiCoherence`（新）：五类检查——悬空归属 / 空缺域 / 未归类 / 过期关联 / 基线落后。

## 技术债清理（commit 149daad1）

上表列的四条技术债全部还掉，并顺手改掉了它们背后真正的浪费。

### 1. 重扫后台化 + 交互路径不再重扫

- `WikiStore.reload()` 变 `async`：列目录 / 读文件 / 解析全在 `Task.detached`，
  主线程只跑 `apply(outcome)` 装索引。`reloadGeneration` 丢弃先发后到的旧快照。
- 保留 `reloadNow()`（同步）只给离屏渲染、验收脚本、`init(autoLoad:)`。
- `create / save / save([...]) / confirm(ids:) / discardDrafts / delete` 全部改走
  `applyChanges(updated:removed:)`：内存增量，不读磁盘。
- 正文 `[[链接]]` 记忆化（`bodyLinkCache`），检索行改按 id 存、只重算改动条目。

### 2. 图谱按输入指纹决定要不要重建

`GraphInput = (标题, 显式关系, 正文链接)`。三者未变就只调 `WikiGraph.updateNodes`
刷 `isDraft`，不重建节点数组与四个邻接字典（240 节点 ≈ 17ms）。
这是「确认草稿」这条最高频路径的关键优化。

### 3. 体检后台化

`WikiCoherence` 拆成 `snapshot(graph:store:)`（主线程，O(条目数)）+
`evaluate(snapshot:root:baseCommit:)`（后台，git + fileExists）。
UI 走 `checkAsync`，面板与主窗口都带代数号防旧报告覆盖。

### 4. 文件拆分

| 文件 | 行数 | 内容 |
|---|---|---|
| WikiWindow.swift | 343 | 窗口骨架 + 三栏共享状态 + 小工具 |
| WikiWindow+Toolbar / +Sidebar / +Center / +Detail / +Curation | 347/310/192/285/102 | 各栏 |
| MindMapView.swift | 409 | 画布、缩放平移、连线、空态 |
| MindMapLayout.swift | 366 | 纯几何布局 + 缓存（无 SwiftUI 类型） |
| MindNodeCard.swift | 174 | 节点卡片 |
| MindMapChrome.swift | 117 | 图例、缩放按钮、自绘小按钮 |

成员刻意不加 `private`（扩展跨文件），边界靠「栏」的语义划分，理由写在
`WikiWindowView` 的头注释里。

## 建档与领域打通（方案 A，commit 64863e10）

### 改动前的缺口

`WikiStore.applyDraft` 构造 `WikiEntry` 时不传 `domains`，`WikiCurator` 提示词里没有
一个 `domain` 字样，`WikiCurationRunner` 建完档也不调 backfill —— 三条都断着，
所以整仓建档的产出 100% 未归类（那 240 条就是这么来的）。

唯一会写 domains 的生产路径：`WikiDomainSeeding.seed`（按域生成，但只覆盖空域）
和 `WikiDomainBackfill.apply`（事后按路径匹配）。

### 改法

- `WikiDomainBackfill.domain(forSources:graph:)`：把路径→域的判定提成公共 API，
  内部把 `resolve(entry:)` 抽成 `resolve(sources:)`，回填与建档共用同一套规则
- `WikiCurationInput.domain`（`DomainContext`: id/标题/包/类数）
- 提示词：user 段写「所属域」，system 段加第 5 条「聚焦域内判断，不写整系统介绍」
- `applyDraft(domainID:)`：create 直接写，update 只在原本为空时补（不冲掉人工归属）
- 整仓建档：每模块按 `module.files` 路径算 hint，同时喂提示词与落盘
- 单条「AI 整理」：`domainContext(for:)` 同样注入
- `DomainModelStore.lockedGraph(root:)`：静态只读加载，不造 ObservableObject

## 修正：「已建档」的判据 bug（commit 618b645f）

上一轮把 `.insights.json` 描述成「纯内容缓存」是错的。它在代码里**同时是
「已建档」的判据**（`freshCount` 只查 `insights.insight(for:url:model:)`）。

后果（用户截图）：清空知识库后，建档面板仍显示
`全仓 2651 / 已建档 711 / 待处理 1940`，点开始会从第 712 个文件继续，
前 711 个文件永远不会再生成条目。

### 真正的根因

两个概念被混成一个：
- 缓存回答「内容读过没有、改过没有」→ 决定要不要重新**理解**（调模型）；
- 条目回答「有没有被知识覆盖」→ 决定要不要重新**建档**。

### 修法

「已建档」= 缓存命中 **且** 知识库有条目引用该文件路径。

- `WikiCurationRunner.run`：`curatedPaths = Set(store.entries.flatMap(\.sources))`
- `WikiRepoIngest.inventory(insights:model:curatedPaths:)`：新增可选参数（nil = 旧口径）
- `WikiCurationRunner.preview(root:curatedPaths:)` 透传
- `WikiIngestSheet.task` 从 store 取并传入
- 「理解文件」阶段仍复用缓存，不重复调模型

### 验收

```
修复后：全仓 2651 · 已建档 0 · 待处理 2651
旧口径：711 会被误判   ← 与线上截图一致
```

### 教训

清理缓存类文件前，先确认它在代码里承担了几个语义。
`.ingest-state.json` 只是进度记录（可清），`.insights.json` 兼具
「内容缓存 + 已建档判据」两个角色 —— 而判据本身有缺陷，
比起删缓存，更应该把判据修成「缓存 + 条目」双条件。

## 「建档卡死」真相：无限重写（commit 1a916f73）

### 现象

17:29 用户报"卡死"。实测：进程在跑、有 Anthropic 请求在飞，但
`round 84→89`、`filesDone 1242→1237`（**倒退**）、`callsUsed 686→696`、条目数**始终 408**，
两个模块的 md 在 17:28/17:29/17:33 被反复重写。

### 根因链

1. `runRound` 把 `module.files` 过滤成**只有待处理文件**（`pending`）
2. `makeDraft` 用这个子集写正文与 `sources`，`mergeMode = .replace`
3. `applyDraft` 的 `.replace` 分支 `updated.sources = sources` —— **覆盖**
4. 上一轮已建档的文件不再被条目引用 → `curatedPaths` 判据（上一轮刚加的）判它待处理
5. 回到 1，无限循环

即：上一轮修的「已建档 = 缓存 + 有条目引用」判据，把这个一直存在的
`sources 被覆盖` 隐蔽 bug 引爆成了死循环。

### 修法

- `makeDraft` 增加 `allFiles` 参数，正文与 sources 用模块**全部**文件
- `WikiCurationRunner` 建 `fullFilesByModule`（scan 的完整结果），写盘时传入
- `applyDraft` 的 `.replace`：`sources` 取并集（防御层，即使传子集也不丢）
- `WikiCurationJob.load`：`running` → `paused`（进程被杀后残留的 running
  会让界面显示永远不推进的"运行中"）
- `finish()`：`store = nil` 移到 `if let store` 之后（原来 reconcileRelations 永不执行）
- 每轮日志加耗时；`progress` 改按 `job.filesDone / totalCandidates` 推进

### 验证

新增「增量合并」自检：同模块两轮写 A+B 与 B+C，最终 sources 必须 A+B+C → 通过。
副本上另外 6 项自检全通过（408 条 / 3112 边）。

### 处置

- 已 `pkill` 停掉震荡中的进程（每分钟 6 次调用、持续缩减条目覆盖）
- 停时 round 89 / callsUsed 696 / 条目 408
- 408 条里被"摘掉文件"的条目会在下次继续建档时自愈（用完整文件列表重写）
- 注意：Debug 编译验证过，**没有**打包发版

## 建档端到端验证（commit d31aefa9）——又挖出三个问题

### 怎么验的

新增 DEBUG 入口 `WikiCurationVerification`：
```
QIYIDE_VERIFY_CURATE=<repo> [QIYIDE_VERIFY_CURATE_ROUNDS=1] [QIYIDE_VERIFY_CURATE_FILES=2]
```
打印「扫描/已建档/待处理」诊断、模型连通性、每轮前后指标、sources 是否缩减。
输出走 stderr —— `print` 重定向到文件是块缓冲，卡住时什么都看不到（这个坑踩过）。

### 验证中暴露的三个真问题

1. **模块数被截断 400**（`wholeRepo` 分支 `maxModules = 400`）
   全仓 918 模块只取前 400，建完后待处理为空 → 判「全仓完成」。
   实测 2650 文件只覆盖 1242。改成整仓不截断（`Int.max`）。

2. **remaining 按候选集算** → `remainingAfterRun = pendingCount`
   候选集一截断就归零 → `status: finished`。
   改成全仓口径 `max(considered - freshCount, 0)`。

3. **模型请求没有总超时**
   `urlRequest.timeoutInterval`（25s）只管「两次数据之间」的间隔，
   流式响应只要还在吐字节（心跳/空行）就永不触发。实测单请求拖过 10 分钟。
   修：`AINarrativeHTTP.session`，`timeoutIntervalForResource = 300`，
   provider 里 4 处 `URLSession.shared` 全换掉。
   **教训**：我第一版加的 `withTimeout` 反而有害——结构化并发在抛超时后
   仍会等那个挂住的请求结束（`bytes(for:)` 不检查取消标志），
   表现为「超时了还卡着」。已删除，兜底只放在网络层。

### 验证结果

```
基线 408 条 → 412 条（新增 4）
sources 缩减：0 条
filesDone 1242 → 1244（单调上升）· failures 0
模型连通 ping 1.4s（慢的是 relate 的大请求，不是网络）
```

对比修复前同口径：`filesDone 1242→1237`（倒退）+ 条目数不变 + 同一 md 被反复重写。

### 成本实测

- 每轮约 5 分钟：全仓扫描 918 模块 + `git log` churn + relate（1 模块）
- 生产配置 240 文件/轮 ≈ 80 模块 → 预计 30-40 分钟/轮
- 全仓 1406 个待处理文件 ≈ 6 轮 ≈ 3-4 小时（可暂停续跑）

### 验证留下的痕迹

知识库 408 → 412 条，新增 4 条真实条目（验证时实际建档产出，不是垃圾数据）。
基线快照在 `/tmp/wiki-baseline.json`。

## 打开大文件卡死（commit 68310ddc，11-03）

### 量化（新增 `QIYIDE_VERIFY_LARGE=1` 基准入口，12.3MB / 20 万行）

| 操作 | 耗时 |
|---|---|
| `textStorage.string` | **0.0ms**（桥接，不复制 —— 原假设错了） |
| `String.hashValue` | **494.3ms** ← 唯一大头 |
| `getLastLines(5)` 于全文 | 0.2ms |
| `enumerateSubstrings(.byLines)` | 38.6ms → 产出 20 万个行区间 |

### 根因链

`GitBlameCoordinator.prepareRefresh` 用 `text.hashValue` 做「文本变没变」的指纹：
- SipHash 必须遍历每个字节 → 12MB 就是 494ms
- 这段在 **@MainActor**，且 `prepareCoordinator` 里 `scheduleRefresh(immediate: true)`
  → **打开文件立刻跑一次**
- 之后每次编辑（0.6s 防抖）再跑一次

表现：一开文件僵半秒，打字也断续。

### 修法

1. 指纹改 `分支|编辑代数|字符数|路径`，全 O(1)；
   编辑代数在 `textViewDidChangeText` 里递增
2. 行级标注加闸门 `maxAnnotatedCharacters = 200_000`：标注是每行一个
   `TextAttachment`，20 万行就是 20 万个对象，超限直接不装、也不进 git blame
3. `CodeFileView` 大文件（>200 万字符）关语法高亮与 minimap（都是全文级工作）
4. `CodeFileDocument.getLanguage()` 加缓存（body 每次重建都会调）
5. `apply()` 用 `mutableString` 桥接，不再经 `.string`

### 待办（没做）

- LSP 仍会对大文件 `didOpen` 全文，服务器解析可能慢；是否按大文件阈值跳过 LSP 同步待评估
- `WikiCurationVerification`（昨天）与 `LargeFileVerification`（今天）都是 DEBUG 入口，
  挂在 `CodeEditApp.init()` 的 `#if DEBUG` 块里

## 大文件高亮：不能关，要异步（11-03，CodeEdit 0d4081d7 + SourceEditor 1c67cb12）

### 上一版的错误取舍

为了不卡，直接把大文件的 `highlightProviders` 置空。用户否掉了：
关掉高亮等于让大文件失去可读性，而问题不在「高亮贵」。

### 行业做法（查证 VS Code）

- `editor.largeFileOptimizations`（默认 true）：门槛 **50MB**，逐项关闭
  tokenization / wrapping / folding / CodeLens / word highlight / sticky scroll
- `editor.maxTokenizationLineLength`（默认 **20000**）：跳过超长行的 tokenize
- tokenization 本身是 view-based + 异步
- 结论：**不是一刀切关高亮**，是「视口优先 + 逐项降级 + 超长行跳过」

### 真正的根因

`TreeSitterClient.setUp` 无条件同步全文解析（主线程，经 Highlighter.init →
HighlightProviderState.init）。注释写「常规源码几十到几百毫秒」——小文件成立，
大文件是几秒。

对照实测（`QIYIDE_VERIFY_HIGHLIGHT=1`，同一份文本切两个阈值）：
```
   2000 行 /   98,669 字符 · 同步  52.9ms · 异步  50.1ms
  20000 行 / 1,046,669 字符 · 同步 477.4ms · 异步   0.1ms
```
按比例，12MB ≈ 5 秒同步阻塞。

### 修法

`setUp` 按 `Constants.maxSyncContentLength`（100 万字符）分流：
- 小文件同步 → 打开即有高亮
- 大文件 `executor.execAsync(priority: .reset)` → setUp 立即返回，
  state 为 nil 期间查询返回空（纯文本），完成后 `setUpFinishedNotification`
  触发一轮视口查询

不会死锁：查询侧 `queryHighlightsFor` 早就用同一个阈值分流了；
死锁只发生在「解析异步 + 查询同步」的组合。

配套：
- CodeEdit 侧恢复高亮，大文件只关 minimap（阈值 200 万字符）
- 保留 git blame 的行级标注闸门（每行一个 TextAttachment，性质不同）

### 体验变化

大文件打开时先显示纯文本，高亮在解析完成后出现（12MB 约几秒）。
这是异步解析的固有代价，换来的是「界面立刻可用」。

### 还没做

- `maxTokenizationLineLength` 等价物：超长行（minified JSON / 单行日志）仍会
  被 tree-sitter 解析。要做需要在 `queryLayerHighlights` 前按行判断并跳过。
- LSP 仍会对大文件 didOpen 全文。
