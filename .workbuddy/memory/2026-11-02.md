# 2026-11-02 · 知识库与领域建模合并：阶段 1（数据打标）

用户的判断是「领域建模和知识图谱有点分离」，方向上我同意，但根因不是窗口多，
而是**同一个「域」有三套互不相认的身份**：

| 层 | 身份 | 存储 |
|---|---|---|
| 领域建模 | `MindNode.id = "domain:service/portrait"` | `domains.locked.json` |
| 架构视图 | `WikiDomain.name`（自由文本，无 id） | `architecture.json` |
| 知识条目 | **没有域字段**，只有 `tags: ["domain","领域"]` | `*.md` |

方案：以 `MindGraph` 为唯一事实源，`WikiEntry.domains` 与
`WikiDomain.domainID` 都指向 `DomainID`（即 `MindNode.id`）。
四阶段：① 打标 ② 合窗 ③ 流水线+体检 ④ 入口收敛。本次只做阶段 1。

## 已落地（阶段 1）

- `WikiEntry.domains: [String]`，frontmatter 键 `domains:`（也兼容手写 `domain:`），
  缺失即空数组，老条目零改动可用。
- `WikiStore`：新增 `entriesByDomain` 索引 + `entries(inDomain:)` / `unassignedEntries` /
  `taggedDomainIDs`。
- `WikiDomainSeeding`：生成时写 `domains = [domain.id]`，正文加「归属」小节；
  跳过规则从「同名即跳过」改成三分支（同域同名 / 无标记 / 被别的域占用并给警告）——
  否则两个域同标题时会互相顶掉且无人知晓。
- `WikiDomainBackfill`（新）：只算不写的归属报告 + `apply` 批量补写。
- `DomainBackfillSheet`（新）：建模窗口「域归属」按钮打开，列出空缺域/可归属/多义/无归属。
- `WikiWindowView` 详情新增「所属域」段（未归类标橙）。
- 验证入口加「打标自检」：frontmatter 往返 + 报告 + 可选写入路径。

## 关键算法：归属判定优先级（被真实数据逼出来的）

第一版按「每个域是否有任一 source 命中」判，真实仓库 240 条上得到
**111 可归属 / 110 多义**——大量本该唯一的条目被判成歧义。原因是兜底域
（按一级包聚合的 `agent`、`service`）会命中所有子路径。

改为三条优先级后 **221 / 0 / 19 / 0**：

1. **同一路径上靠前的业务段优先**：`agent/service/X.java` 同时含 `agent` 与 `service`，
   它属于 `agent` 产品线，`service` 只是子目录名；
2. **同起点时长键优先**：`service/portrait` 胜过 `service`，兜底域抢不走具体域认领的路径；
3. **不同 source 命中不同域才算多义**：这才是真正的跨域条目。

匹配必须按「段」而非子串：`agent/suggest` 不能命中 `agent/suggestion`。

## 验证数据

- 合成仓库（3 域 + 4 条目）：可归属 2 / 多义 1 / 无归属 1 / 空缺域 1 —— 与设计一致；
  写入后 md 出现 `domains: domain:agent/suggest`，域索引 AI画像 1 / AI建议 1 / AI客服 0。
- 真实仓库（saas，240 条，已锁定模型）：**已标 0 / 可归属 221 / 多义 0 / 无归属 19 / 空缺 0**。
  19 条无归属是 `app/proxy`、`sql/`、`admin-ui/lib`、`app/api`、`scripts/` ——
  确实在已建模的域之外，保持未归类是对的。
- 打标往返：通过。

## 阶段 2（同日下午）：一页三模块

知识库窗口变成唯一主界面，中间栏 `CenterMode` 从 2 种扩到 3 种：**导图 / 图谱 / 架构**，
导图模式下再挂一个「视角」下拉（建模 + ViewSpec 预设），复用 `MindMapView`
（`displayGraph` + `graphToken` + `isReadOnly` 三参数正好够用）。

- 左栏：**领域段 + 条目段放在同一个 ScrollView 里**。拆两个各自滚动时，领域段被
  `maxHeight` 裁掉半行、看起来像渲染坏了，而且用户得猜哪边能滚。
- 左栏条目按 `selectedDomain` 过滤；`__unassigned__` 作为伪域哨兵，
  避免再加一个 Bool 状态位。
- 导图的选中回传用 `Binding` 适配：节点 → 域，**模块节点归到父域**
  （否则点模块时左栏过滤清空、右侧停在模块，三栏各说各话）。
- 右栏新增 `domainDetail`：归属包 / 负责人 / 判定依据（带权重）/ 模块 / **该域知识条目**。
  这是「结构」与「知识」的接缝，之前分处两个窗口。
- 导图模式的操作区：识别/重新识别、锁定、⋯（生成缺失知识 / 域归属 / 解锁）。
- 菜单收敛：`⌥⌘K 打开知识库`（主入口）+ `⌥⌘D 全屏建模`（大画布做人工锚定）。

### 打标未完成时的显示（重要）

240 条全没打标时，域下面的计数全是 0。第一版直接把 0 渲染成橙色的「缺口」，
看起来像「整个知识库都缺」——其实是「还没建立归属」。
改为：`taggedDomainIDs` 为空时显示「—」，并在领域段末尾给一条
「240 条知识未标归属 · 去补写」的橙色入口；列表空态文案也区分两种情况。

### 离屏渲染整窗：必须用 NSHostingView，不能用 ImageRenderer

`ImageRenderer` 画不了带原生控件的界面——`Button`/`Picker`/`HSplitView` 会被整块
替换成「禁止」占位符，实测整窗变成一张巨大的红色斜杠图。
改为挂到屏幕外的真实 `NSWindow`（`origin: -6000,-6000`）+ `orderFrontRegardless`
+ 等 1.6s 让 SwiftUI 完成首帧 + `cacheDisplay(in:to:)`，控件全部正常。
入口：`QIYIDE_VERIFY_WIKI=<repo>`，可选 `QIYIDE_VERIFY_WIKI_OUT` 指定输出。

## 阶段 3：流水线状态条 + 一致性体检

- `WikiCoherence`（新）：五类检查——悬空归属 / 空缺域 / 未归类 / 过期关联 / 基线落后。
  **只报确定的问题**：条目 source 是业务包路径（`agent/suggest`）时无法判存在，
  只检查带扩展名的文件路径，宁可漏报目录类 source。
  一条都没打标时不报「8 个域全空缺」，只报一条「240 条未标归属」——否则满屏误报。
- `WikiCoherenceSheet`（新）：分组列出 + 唯一批量修复「清除悬空归属」，
  其余只给提示（空缺该生成还是该删域，是人的判断）。
- 顶部状态条：识别 → 锚定 → 知识 → 审核，**全部由数据推导、不落盘**，
  所以不会出现「状态说完成、实际没做」；右侧显示体检计数。
- 真实仓库实测：`未归类 1 · 过期关联 17`，抽查两条被判定过期的文件确实已不存在；
  baseCommit 与 HEAD 相同，基线检查正确未触发。
- 合成仓库实测：`悬空归属 1 · 未归类 1`，幽灵域 `domain:does/not/exist` 被正确抓出。

## 阶段 4 + 代码审查（收尾）

**完成的功能**

- 条目「关联代码」可点开（区分：包路径不可点 / 文件存在可点 / 文件失效橙色标注）。
- 导出（Markdown 大纲、JSON）从独立窗口搬进知识库工具栏。
- 删除 `DomainModelWindow.swift`（587 行重复 UI），菜单只剩「打开知识库…（⌥⌘K）」。
- 条目编辑器补「所属域」下拉——之前只能在 frontmatter 手写。

**审查发现并修复（6 处，均有实测）**

| # | 问题 | 修法 | 效果 |
|---|---|---|---|
| 1 | `save(entry)` 里 `reload()` 重读全部 md | 新增 `upsert`：只改内存 + 重建索引/图 | 单条保存 225→76ms |
| 2 | `ISO8601DateFormatter()` 每条目构造两次 | 静态复用 | reload 472→225ms |
| 3 | `bodyLinks` 每条目编译一次正则 | 静态复用 | 与 2 合计 |
| 4 | `DomainBackfillSheet` 自带 store，写完父页面不刷新 | 共用父 store + onChanged | 修 bug |
| 5 | `filteredEntries` 一次 body 算 3 遍 | 列表只算一次传入 | 240 条少扫 480 次 |
| 6 | 到处 `!taggedDomainIDs.isEmpty` 现造 Set | 加 `hasDomainTags`（O(1)） | — |

**可读性**

- `WikiWindow.swift` 1776 → 1480 行：抽出 `WikiDomainDetailView`（150 行）、
  `WikiEntryEditor`（146 行）、`WikiSmallViews`（WikiChip/WikiSection，样式单点维护）。
- 生成知识由「每条 2 次全量重扫」改为「准备完一次落盘」。

**最终性能（Debug、240 条知识、8 个域，Debug 会放大常数）**

```
reload 245ms（一次性/批量）  单条保存 76ms  体检 24-28ms
投影 0.15ms/视角            布局 0.2ms(42 卡片)   归属报告 118-126ms（仅打开时）
```

**仍存的技术债（已确认，未做）**

- `reload()` 仍同步在主线程（240 条约 245ms）；条目涨到千级时应改成后台解析。
- `WikiWindow.swift` 仍有 1480 行，下一步应按 三栏 拆成 sidebar / center / detail 三个 struct
  （需要放开 `@State` 的 fileprivate 边界，改动面大，留给专门一轮）。
- `WikiCoherence.check` 在主线程跑 git + 约 1900 次 fileExists（24ms），可挪后台。
- `MindMapView.swift` 1025 行（布局 + 视图 + 卡片 + 控件）。
