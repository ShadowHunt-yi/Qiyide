- 根因：`updateNoResultsState` 挂在 `viewDidLayout`，每次布局都读 `outlineView.numberOfRows`；
  而"全部展开"要连续插入上万行，每次插入触发布局 → 又强制算行数 → O(n²)，界面冻结。

## 性能复查：热点路径的复杂度（13:58-14:06）

### 修掉的真实 n² / n·m
1. 文件树数据源 O(k² log k)：`child(index:)` 每取一行都重建整层（排序 + 紧凑链）。
   改为 `displayChildrenCache` 按数据「代」缓存；失效点：reloadData、过滤变化、文件事件、菜单文件操作。
   注意粒度：`invalidateDisplayChildrenCache` 只清展示缓存，`invalidateCompactItems` 才清紧凑条目
   （否则每次文件变动都换条目身份，已展开的链条目会被折叠）。
2. LSP 编辑 O(n·m)：每条 TextEdit 都复制整串并从头数行。改为一次 `LineOffsetIndex`（行首数组），
   区间一次性算好，倒序应用。
3. 附件批量移除 O(n²)：逐个 remove(at:) 搬移数组。改为 filter + removeAll 单遍。
4. compactItem 反查 O(缓存×链长)：改用 `compactItemByMemberPath` 路径索引（选中/揭示热路径）。
5. git status 进程放大：文件系统事件每批都 `refreshAllChangedFiles`。新增
   `SourceControlManager.scheduleChangedFilesRefresh()`（300ms 取消式合并），DirectoryEvents 改走它。

### 顺带优化
- GitBlameAnnotation：CTLine/宽度改为按需构建 + 缓存（原来刷新时为每一行预排版，大文件几十 ms）。

### 复核为「非 n²」的路径
getFile（字典 O(1)）、diff 解析/对齐（O(n)）、blame 解析（O(行数)）、Markdown 渲染（O(n)，已移后台）、

## 全部展开卡死：改为分批增量（14:28-14:33）

用户反馈：点下箭头（全部展开）直接卡死。上一轮只删掉了 viewDidLayout，未解决根因。

根因：`outlineView.expandItem(item, expandChildren: true)` 是**同步递归**，会在一帧内插入上万行，
主线程被独占且不可取消——不是"慢"，是整段主线程任务。

修复（ProjectNavigatorViewController）：
- 改为分批增量：每批最多 200 项 → `DispatchQueue.main.async` 排到下一个 runloop，批与批之间让出主线程；
- 逐层推进：每层收集「可展开且未展开」的行快照，最多 64 层；
- 可取消：`cancelExpandAll()` 用 token 失效在途批次；收起、reloadData 都会调用它；
- 安全上限：总行数 > 60000 停止；单个目录子项 > 8000 跳过并计数（一次展开上万行仍会卡）；
- 每批用 `NSAnimationContext.runAnimationGroup { duration = 0 }`，避免跨批次持有 grouping；
- 记录：`treeExpand` 埋点带 rows/passes/skipped；OSLog category=Navigator 记录开始/结束/取消与耗时。

注意：`autosaveExpandedItems` 在展开期间关闭、结束/取消时恢复（避免每批写 UserDefaults）。

## 展开卡死：hang 报告定位到磁盘 stat 放大（14:32-14:36）

用户提供 hang 报告（PID 16823，旧包）：main thread 卡在
`expandAllFolders → expandItem:expandChildren: → _expandItemEntryChildren…` 递归，
内部反复走 `numberOfChildrenOfItem → displayItems → displayChildren → getOutlineViewItems
→ childrenOfFile → loadChildrenForFile → contentsOfDirectoryAtURL`（磁盘枚举），
以及 `sortedChildren → CEWorkspaceFile.isFolder → resolvedURL → URL.resourceValues`（磁盘 stat）。

真正的放大器：`Array<URL>.sortItems(foldersOnTop:)` 把 `resourceValues(.isDirectoryKey)` 写在**比较器内部**，
排序 n log n 次比较 → n log n 次 syscall；目录越大越慢，且被递归展开放大。

实测（/System/Library/PrivateFrameworks，2126 项）：
- 旧（比较器内查资源）：477.8ms
- 新（预取排序键）：43.2ms
- 约 11×

修复：
1. `Array+SortURLs.sortItems`：预取 (isDirectory, lastPathComponent) 后排序。
2. `sortedChildren`：预取 (isFolder, name) 元组，避免比较器里重复访问 lazy 属性。
3. `expandAllFolders`：分批 + 12ms/帧时间预算 + 每批 200 项上限 + 可取消（token）+
   单目录 >8000 子项跳过 + 总行数 >60000 停止（详见上一条记录）。

后续可做：把枚举时已拿到的 `.isDirectoryKey` 透传给 CEWorkspaceFile，省掉每文件一次 stat。
